APP 數據追蹤就靠它，Firebase 心得分享

最近公司開發了一款新的APP，而我以數位廣告操作及營運數據建置分析的角色進入開發團隊。之前多碰的是網站，其實根本沒什麼接觸 APP 的機會。所以剛好趁這次的機會大量嘗試及學習，瘋狂的詢問 Google 、facebook AM，去聽 Google 的 Firebase 分享也是先整理一堆問題，纏住講師一直問，因為一開始真的對 APP 很陌生。

Firebase 是 Google 收購的一項服務，是一個同時支援 Android、iOS 及APP雲端開發平台，原先可以透過埋設 SDK 在 Google Analytics ( GA ) 收集數據，後來調整為透過 Firebase 來收集數據。

從開發到上線，以及到現在維護優化，接觸這項工具一段時間了，這邊針對 Google Analytics For Firebase 整理三個有趣的發現跟大家做分享：

1. Firebase 跟 AdWords 的事件轉換優化

Firebase 收集到的 APP 數據，用來與 AdWords 的廣告，能做到非常良好的串接。 Google 有開發一個有趣的廣告格式，叫 Google 通用應用程式廣告活動（Google Universal App Campaigns)，為什麼說它有趣呢？ 大家可以參考 被取代的進行式：我被 Google 取代的鬼故事 這篇文章，便會讚嘆 Google 今年提的 AI First 。

離題了，這個廣告可以幫助廣告主獲取 APP 下載，你可以去做優化的是 CPI ( Cost Per Installation )，但我們可以透過 Firebase 設定 APP 裡面的事件，像是首次開啟 APP、註冊、等級到達 30 級，並串接到 AdWords 讓我們知道透過廣告除了下載外，還能帶回哪些其他的轉換。

而後 Google 也推出所謂的 UAC 2.0 ，如果你有從 Firebase 匯入轉換事件到 AdWords，就能針對單一事件的轉換成本做優化，例如你想找到註冊成本為 100 元的用戶，只要有設定事件並匯入 AdWords ，Google 就能幫你優化這項轉換成本，非常厲害。

( 圖片來源：commons.wikimedia.org )

2. Funnels 報表並沒有那麼 Funnel

以往在 Web 端，我們很常看每個流程間，網頁或事件的轉換及流失率。 Firebase 裡也可以看見像是這樣的分析報表，你可以把設定好的事件拉進來看。但你會發現：為什麼不會呈現一個漏斗形狀？其實是因為這裡每個事件是計算總量，排在一起是每個事件總量的排列而已。

舉例來說就是，假設想觀察的流程是 A 事件→ B 事件 → C 事件的留存狀況。在 Firebase 是：完成 A 事件有 60 人、完成 B 事件有 40 人、完成 C 事件有 30 人，但不會是我們想知道的：完成 A 事件的 60 人接下來有完成 B 事件的有幾人，那這些人又有去完成 C 事件的有多少。

那這樣有什麼解決方法呢？第一，你的流程必須是封閉式的，也就是使用者只能從 A 事件進入，這樣就能看出轉換流失狀況。第二、Google 會推薦你將 Firebase 都匯入 BigQuery，但是儲存跟查詢要錢就是了 ……

3. 好用的 Dynamic Links

透過 Firebase 後台，我們可以設置 Dynamic Links，它有什麼功能呢？一般來說，我們在網址代上參數，用來追蹤進入網站後續行為。但如果要進入 APP ，通常會遇到的狀況是，如果我沒有安裝，就必須先進到商城，安裝完成才能進入 APP，這中間很容易造成追蹤中斷 ( 因為你追蹤不到商城的資料 )。

這時你可以到 Firebase 後台設置 Dynamic Links，它可以設定參數，讓你做不同用途時的辨別，另外這個連結點擊後，可以自動判斷用戶的手機裝置，引導至 Android 或 IOS 的商城。最後是，你可以透過這個 Link 在後台查看完成了哪些事件轉換 ( EX：下載、首次開啟、註冊 ) ，非常方便，不過缺點就是我覺得 Firebase 生成的網址長得有點醜。

總結
